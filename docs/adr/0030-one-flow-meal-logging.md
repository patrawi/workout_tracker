# One-flow meal logging — no review step, no portion modes, no visible ranges

The meal-photo flow collapses to: photo + optional additional info → VLM estimate → auto create + confirm → a result screen showing the photo and single central nutrition numbers, with per-component provenance for post-hoc correction. We deleted the Estimated/Measured portion-mode toggle, the low/central/high weight editing UI, the eaten-fraction quartile pickers, and the review step because the owner judged range editing the worst UX in the app — a user who weighed their food had to re-fix the AI's ranges by hand — and the review step existed mainly to host that editing. The frontend now sends the VLM's central weights as degenerate point ranges (`low = central = high`, which validation already accepts) with fraction defaulting to All unless the after photo produced a proposal, so the backend contract, the interval calculation engine (ADR 0008/0018/0019), and the database schema are unchanged; intervals remain an internal representation and `portion_mode` is frozen to "estimated" for new logs. Never-block survives as: a failed/unavailable analysis stays on the form for retry (the photo flow no longer offers manual component entry — text logging via AIInput is the manual path), and a failed auto-confirm keeps a manual "Confirm & log" fallback on the result. Also fixed here: the `useMealObservations.interpret` wrapper silently dropped the `user_note` argument (ADR 0028), so user-stated weights never reached the VLM in the released UI — which is why anchoring looked broken; live E2E confirms the constraint anchoring works once the note is actually delivered.

Two follow-ups fell out of live use the same day. First, auto-confirm made every observation confirmed, which tripped ADR 0026's "confirmed observations cannot be re-resolved" guard and broke the only correction path — resolving a component on a confirmed observation now re-finalizes instead of rejecting: the new revision is marked confirmed, older confirmed revisions are superseded, and nutrition_logs is re-dual-written so daily totals follow the fix. Second, the vector auto tier let BaoWio's bare ingredient names ("ข้าวเหนียว", 0.879) edge out ThaiFCD's preparation-qualified rows ("ข้าวเหนียว, นึ่ง", 0.796) for cooked-dish queries, feeding unit-suspect macros into estimates — the vector auto decision now uses a vendor-adjusted similarity (`similarity − providerRank × 0.1`), so BaoWio must genuinely outrank ThaiFCD by the handicap or the component goes to the picker with the kind prior in the meantime.
