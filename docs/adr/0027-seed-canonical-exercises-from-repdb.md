# Seed canonical exercises from RepDB and ground gym profiles in equipment availability

Phase 2 of PAT-56 (per-gym equipment/substitution profiles) must answer "can the user perform exercise X at gym G", but exercise names in logs and plans are free text and no exercise/equipment catalog existed — the biggest design risk flagged at PAT-56. We seed a Canonical Exercise catalog from the RepDB free-tier dataset (601 exercises, evidence-checked against the owner's 25 real log names — dumbbell-heavy with granular machine types; the 179 null-equipment rows are all bodyweight, and "Machine Reverse Fly" becomes a manually authored `manual` row), imported by a script that fetches the pinned `exercises.json` at run time — never a committed CSV, because the repo is public and RepDB's license forbids redistributing the dataset or a derived one (Free Tier term 3) while in-app use with attribution is free. Workouts anchor onto the catalog through a nullable `canonical_exercise_id` plus `match_tier`, resolved by a three-tier matcher (user-attested alias exact → lexical token overlap → pgvector over name_en on its own scale) at confirm time and never blocking: unmatched names stay free text with tier `gap`. A Gym Profile is a per-gym set of equipment-type ticks; Equipment Availability derives from ticks ∪ exercises actually logged at that gym, and a gym without a profile stays unrestricted (additive override, per the glossary). Substitutions are coach-side only — a lookup tool the coach calls when planning — and Derived Substitution from same primary muscle + available equipment; no curated pairs table and no log-time warning in v1.

## Considered Options

- smyrdev/exercises-dataset (1,324 exercises, MIT, redistribution-friendly) as the base — rejected: its machine tagging is coarse ("machine"/"leverage" buckets), while per-machine granularity is the entire point of Phase 2; RepDB names actual machine types (`chest_press_machine`, `pec_deck`, `leg_curl`, …). RepDB's no-redistribution term is handled by fetch-at-import instead of vendoring.
- A three-bit Free/Station/Machine gym vocabulary — rejected in grill: the owner's two regular gyms differ in which machines they have, so coarse bits make both profiles identical and Phase 2 delivers nothing. Settled on per-equipment-type ticks (~24 curated values from the RepDB vocabulary, covering every logged name and plan exercise); the three groups are UI presentation only.
- Curated substitution pairs (converting the CONTEXT.md Upper Flex prose rules to data) — deferred: those rules are mostly fatigue/preference-based, not equipment-based; derived matching covers the equipment cases. Add a pairs table only when a real case defeats derivation.
- Log-time substitution warning in ReviewModal — deferred: the substitution decision actually happens when the coach plans or prescribes a session; a log-time warning would touch ReviewModal for little v1 value.

## Consequences

- In-app attribution owed: "Exercise data by RepDB (repdb.co)" beside the existing CC BY-SA line. Their images are never imported (term 5 also bars generative-AI use), nor are instructions or DE/ES names — lean fields only, re-fetchable on re-import.
- Vector thresholds start provisional and must be calibrated on known-answer queries against this catalog (as the nutrition matcher was on 2026-09-29); only `name_en` is embedded — no Thai alias text feeds embeddings.
- Aliases grow only from real usage: the seed is the 25 already-logged names mapped manually once; every future `gap` gets resolved by hand into the alias table. No bulk translation of catalog names exists.
- Availability is evidence-based: `available(gym, exercise) = equipment(exercise) ∈ profile ticks(gym) OR ∃ logged workout of that exercise at that gym` — the coach can trust that anything the user played there is really playable.
- `coach_plan` is deliberately not anchored by FK; plans are matched on read, and only immutable logs carry the anchor.
