# Human portion constraints at interpret time

`POST /api/meal-observations/interpret` accepts an optional free-text `user_note` (≤500 chars) alongside the menu name and photos, and the VLM adapter injects it into the user message as authoritative constraints that its `weight_g` proposals must anchor on; the note is persisted on `meal_observations` when the observation is saved. We chose prompt-level constraint anchoring over treating the note as evidence rows or engine inputs because a 2026-10-06 human-judged arena on one dish showed the same model estimating 620 kcal with human constraints vs 760 kcal without (≈20% information value) and a constraint-free run inflating fat to 46.9 g with no visual evidence — while the VLM stays an evidence proposer that never computes macros (ADR 0017), its weight ranges previously ran entirely constraint-free. The note is optional so the no-note prompt stays byte-identical, is capped to bound the prompt-injection surface, and is stored because the (photo, constraints, proposal, user corrections) tuple is the raw data for future few-shot calibration; the menu name is additionally declared a weak prior so category assumptions (e.g. oily "ข้าวมันไก่") cannot inflate portions beyond visible evidence.
