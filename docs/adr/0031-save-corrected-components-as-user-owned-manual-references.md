# Save corrected components as user-owned Manual References

Kind-prior estimates are systematically wrong for dishes the owner eats repeatedly (measured 2026-10-18: หมูแดดเดียว priced from the `main` prior at ~103 kcal/50 g vs ~145 kcal real), and `updateComponentMacros` corrections were thrown away at the end of each meal, so the same dish re-missed every time — the catalog has no Thai street-dish rows (search for "หมูแดดเดียว" returns หมูสามชั้น, ข้าวแต๋น, ไส้กรอก) and its only lean rows are raw, which the raw-state guardrail rightly demotes. We now let a user tick "บันทึกเป็น reference" in the existing macro-edit form: the corrected macros ÷ consumed mass (weight × consumed_fraction) become per-100 g values stored as a Manual Reference (`provider="manual"`, nullable `user_id` on `nutrition_references`), matchable only for its owner via `user_id IS NULL OR user_id = me` with a +0.05 owner similarity bonus (mirror of the BaoWio handicap, opposite direction). This is the ADR 0026 upgrade path ("learn corrections from the user's own logged meals"), realized manually instead of via a few-shot phase.

## Considered Options

- Global shared corrections (no `user_id`) — rejected: with Google multi-user login, one user's home recipe would silently price everyone's meals.
- Separate user-refs table — rejected: splits the matcher's source, adds a second embedding column and index for no modeling gain; one nullable column scopes the query in one line.
- Require at least one edited macro before allowing save — rejected: even a weight-only correction is worth saving, because the dish name alone stops future components from missing into wrong references (upsert updates values on the next edit).
- Raw→cooked conversion machinery to unlock lean rows — rejected (2026-10-18 test): the catalog gap is data, not math; manual references plus later curated USDA import (offline, `provider="usda"`) cover it without new conversion code and without violating the no-silent-raw→served stance.

## Consequences

- Identity is `(user_id, lower(trim(name_th)))` with the unique index widened to `(provider, provider_food_code, version, user_id)` — Postgres treats NULL user_ids as distinct, so global rows keep the old guarantee while two users may save the same dish name; saving the same name again updates the row and re-embeds it (`thaifcdEmbedText` convention, text-embedding-004 768-dim), choosing a new name intentionally creates a new reference — no rename primitive, no management UI in v1 (delete waits for real pain).
- Guards on save: consumed mass ≥ 10 g, finite non-negative macros, kcal/100 g ≤ 900; per100 is derived from the component's stored `consumed_weight_g` (already served × fraction) ÷ contribution, stored at full `real` precision and rounded only for display (no double-rounding), while the current observation keeps the user's exact edited macros — references affect only future matches, never re-resolve past observations.
- The reference-search endpoint, matcher, and all three retrieval queries (`findByFoodCode`, `listReferences`, `searchByEmbedding`) gain user scoping (`user_id IS NULL OR user_id = me`); owner rows get a +0.05 similarity bonus in both lexical and vector tiers (vector: above the shared 0.7 ambiguity floor — the floor stays put), and are **exempt from the over-dense kind-band demotion** (user authority over their own numbers per ADR 0019; the ≤900 save guard caps typos) while the raw-state penalty applies unchanged — a manual reference can still lose a race, just never be demoted for its own density.
- An embedding failure on save is non-fatal: the row persists with NULL embedding and the existing backfill script (which targets NULL embeddings only) recovers it; lexical matching works meanwhile.
